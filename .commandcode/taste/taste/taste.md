# Taste
- Wants the agent to read and fully understand the codebase first (structure, data model, data flow, and surfaces) and restate that understanding before any work or recommendations begin — explicitly asks "understand my project" rather than having the agent assume prior context. Confidence: 0.5
- Wants a plan written and approved before large multi-step work begins — explicitly says "plan first" when a request spans many parts (demo data, several screens, verification, and a report), rather than diving straight into implementation. Confidence: 0.6
- Prefers using the latest stable major version of frameworks (e.g. Next.js 16 over Next.js 15), not older versions. Confidence: 0.6
- Prefers the modern flat ESLint config style (`eslint-config-next/core-web-vitals` / `/typescript`) over the legacy `FlatCompat` wrapper when on Next.js 16. Confidence: 0.5
- When asked to check for errors, wants a comprehensive project-wide review covering compile/type errors, UI issues, and routing — not just a fix for the single reported bug. Confidence: 0.7
- Treats cross-surface number correctness as the highest-priority acceptance criterion for the whole system: buying must raise inventory, selling must lower it, and dashboard, inventory, sales, invoices, customers, suppliers, payments, profit & loss, and reports must all reconcile to identical figures (dues, paid, stock, revenue). Wants this proven end-to-end — e.g. a re-runnable QA/audit check that recomputes figures from the raw ledger data — and documented in a written report with the real numbers and any bugs found. Confidence: 0.65
- Expects fixes to be verified by actually running the app (full build + serving every route and confirming HTTP 200) rather than stopping at a clean typecheck/lint. Confidence: 0.7
- Displays in invoices/receipts must faithfully reflect what the user actually entered — quantity shown in its original unit (kg stays kg, tons stays tons) and the price shown as the per-unit price in that same unit — rather than forcing everything into a single normalized unit (e.g. tons) that inflates or confuses the figures. Confidence: 0.8
- Wants the whole app to measure each product category in its own natural unit of sale — steel in kg, cement per bag — with quantities stored, computed, and displayed directly in that product's unit; explicitly rejects a global "ton" unit system and any kg↔ton conversion logic anywhere. Confidence: 0.9
- The business spans multiple product categories with different units (steel, cement, …), so the data model and generic UI copy must not be hardcoded to a single commodity like steel. Confidence: 0.7
- Wants seed/mock data to comprehensively exercise every module and function of the app — all products/items/qualities, kg and ton units, partial vs. full vs. unpaid purchases, multi-line invoices, customer advances and dues, low-stock states — rather than minimal or empty placeholders; the user later reverted the shipped demo to a deliberately minimal seed (see the minimal-demo bullet below), so this reads as a testing-coverage preference, not a final-state one. Confidence: 0.35
- For a full business demo the seed should run on multiple suppliers and multiple customers (e.g. three, one per product category) with a payment mix on BOTH sides — fully paid, partially paid (dues), and unpaid purchases and sales plus a matching payment journal — even though an earlier minimal seed used a single supplier/customer pair for simplicity — and the user ultimately reverted to exactly that minimal state for the shipped demo (see the minimal-demo bullet below). Confidence: 0.3
- Wants stock control to be source-aware: stock is not one blended pool per item — each purchase is a lot attributed to its supplier/mill/company, and when selling the operator must be able to pick exactly which source's stock a line comes from. Confidence: 0.85
- Prefers the source dimension to be the existing supplier/mill list (the company the purchase came from), not a separate free-text factory/company field. Confidence: 0.7
- Wants per-source enforcement and costing, not just labeling: when a source is chosen on a sale line the quantity is limited to that source's remaining stock of the item, and COGS/profit uses that source's actual landed cost rather than a blended average across all sources. Confidence: 0.75
- Wants the chosen source/mill printed per line on customer-facing surfaces — printable invoice, sale detail, live preview, and list rows — so the customer knows which mill the goods came from. Confidence: 0.7
- The "selling price" shown in inventory should be the same purchase-recorded sell price that invoices use (weighted across that item's lots) — displayed consistently on the Inventory page, per-source stock pickers, and invoice lines — rather than a realized average of past sales. Confidence: 0.8
- When the user says "change the whole X system", expects the feature to be carried end-to-end through every surface — data model, store/money math, entry form, list pages, detail modal, printable invoice, and report/customer-balance figures — so no surface shows stale or inconsistent totals. Confidence: 0.8
- When a new sale/invoice is created, its exact time must be recorded automatically by the store at save (a `createdAt` ISO timestamp stamped on the record) rather than entered manually or left absent — every new sale should carry one so the lists and the printed bill can show it. Confidence: 0.8
- Wants customer money tracked per invoice, not pooled into one customer balance: when the same customer buys on different days, each sale stays a separate bill with its own Paid/Due, and a payment should be allocatable to a specific invoice. Payments recorded without an invoice target should settle the customer's oldest unpaid invoice first (FIFO), then spill to the next — so two bills never merge. Confidence: 0.85
- Expects a "receive payment" action wherever invoices are viewed (invoice list rows, invoice detail modal, customer ledger) that records a payment against that exact bill inline with the remaining due prefilled — not only from a separate Payments page. Reaffirmed when asking for a dedicated Receive/Receive Payment button on every unpaid Sales/Invoices row (desktop and mobile) sitting next to Open, hidden once a bill is fully paid. Confidence: 0.85
- When extending a shared component (e.g., adding new size tiers to a common Modal), preserves existing default behavior exactly so no other screen that uses it changes appearance; expands only by opt-in parameters. Confidence: 0.85
- Expects finished work to be committed to git when asked to "add and commit": stages everything (`git add -A`) and creates one descriptive commit summarizing the whole change set, rather than leaving work uncommitted or asking for commit-message input. Confidence: 0.6
- Wants git commit messages written in a playful/cute tone — a whimsical headline plus light, friendly bullet summaries with humor ("every number learned to shake hands", "one happy supplier") — rather than dry conventional phrasing; explicitly asked for a "very cute commit message" when requesting commit-and-push. Confidence: 0.5
- Wants the main dashboard's profit metric to be NET profit on a realized/cash basis, not gross or accrual: an invoice's profit must count only when the customer actually pays their dues (money in hand, matched to the invoice the payment settles), and whole-depot net is after shop expenses — explicitly asked to "not show the gross profit" and instead count profit as customers clear their payments. Confidence: 0.8
