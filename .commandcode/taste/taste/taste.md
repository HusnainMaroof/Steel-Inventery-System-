# Taste
- Prefers using the latest stable major version of frameworks (e.g. Next.js 16 over Next.js 15), not older versions. Confidence: 0.6
- Prefers the modern flat ESLint config style (`eslint-config-next/core-web-vitals` / `/typescript`) over the legacy `FlatCompat` wrapper when on Next.js 16. Confidence: 0.5
- When asked to check for errors, wants a comprehensive project-wide review covering compile/type errors, UI issues, and routing — not just a fix for the single reported bug. Confidence: 0.7
- Expects fixes to be verified by actually running the app (full build + serving every route and confirming HTTP 200) rather than stopping at a clean typecheck/lint. Confidence: 0.7
- Displays in invoices/receipts must faithfully reflect what the user actually entered — quantity shown in its original unit (kg stays kg, tons stays tons) and the price shown as the per-unit price in that same unit — rather than forcing everything into a single normalized unit (e.g. tons) that inflates or confuses the figures. Confidence: 0.8
- Wants the whole app to measure each product category in its own natural unit of sale — steel in kg, cement per bag — with quantities stored, computed, and displayed directly in that product's unit; explicitly rejects a global "ton" unit system and any kg↔ton conversion logic anywhere. Confidence: 0.9
- The business spans multiple product categories with different units (steel, cement, …), so the data model and generic UI copy must not be hardcoded to a single commodity like steel. Confidence: 0.7
- Wants seed/mock data to comprehensively exercise every module and function of the app — all products/items/qualities, kg and ton units, partial vs. full vs. unpaid purchases, multi-line invoices, customer advances and dues, low-stock states — rather than minimal or empty placeholders. Confidence: 0.7
- Within that comprehensive seed, prefers counterparties to be kept minimal so the flow is easy to understand — a single customer and a single supplier, with all sample purchases (even across different products like steel and cement) attributed to that one supplier. Confidence: 0.7
- Wants stock control to be source-aware: stock is not one blended pool per item — each purchase is a lot attributed to its supplier/mill/company, and when selling the operator must be able to pick exactly which source's stock a line comes from. Confidence: 0.85
- Prefers the source dimension to be the existing supplier/mill list (the company the purchase came from), not a separate free-text factory/company field. Confidence: 0.7
- Wants per-source enforcement and costing, not just labeling: when a source is chosen on a sale line the quantity is limited to that source's remaining stock of the item, and COGS/profit uses that source's actual landed cost rather than a blended average across all sources. Confidence: 0.75
- Wants the chosen source/mill printed per line on customer-facing surfaces — printable invoice, sale detail, live preview, and list rows — so the customer knows which mill the goods came from. Confidence: 0.7
- The "selling price" shown in inventory should be the same purchase-recorded sell price that invoices use (weighted across that item's lots) — displayed consistently on the Inventory page, per-source stock pickers, and invoice lines — rather than a realized average of past sales. Confidence: 0.8
- When the user says "change the whole X system", expects the feature to be carried end-to-end through every surface — data model, store/money math, entry form, list pages, detail modal, printable invoice, and report/customer-balance figures — so no surface shows stale or inconsistent totals. Confidence: 0.8
- Wants customer money tracked per invoice, not pooled into one customer balance: when the same customer buys on different days, each sale stays a separate bill with its own Paid/Due, and a payment should be allocatable to a specific invoice. Payments recorded without an invoice target should settle the customer's oldest unpaid invoice first (FIFO), then spill to the next — so two bills never merge. Confidence: 0.85
- Expects a "receive payment" action wherever invoices are viewed (invoice list rows, invoice detail modal, customer ledger) that records a payment against that exact bill inline with the remaining due prefilled — not only from a separate Payments page. Confidence: 0.75
- When extending a shared component (e.g., adding new size tiers to a common Modal), preserves existing default behavior exactly so no other screen that uses it changes appearance; expands only by opt-in parameters. Confidence: 0.85
