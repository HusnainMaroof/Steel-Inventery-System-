# Taste

## Organization & architecture
- Prefers decomposing large, multi-role components (500+ lines doing several jobs — list, modal, add-item cascade, line items, totals in one function with ~15 state pieces) into focused components where each concern gets its own visual container, with the page becoming a thin state owner composing them. The stated payoff is maintainability: each piece becomes independently reviewable instead of one giant diff, and each concern reads/previews in isolation. Confidence: 0.9
- In that decomposition, prefers extracting shared derived-data logic into a hook (e.g. `useSaleDraft`) that owns the lookups and small state slices, rather than duplicating store access inside child components; children receive the specific slice/handlers they need via props. Confidence: 0.8
- Before a large refactor, confirms scope decisions with the user (file split vs. visual-only-in-one-file; whether new behavior like quick-fill buttons is in scope) and implements in a staged/build order from lowest-risk extraction to the most layout-heavy piece. Confidence: 0.8
- Fixes small pre-existing bugs (e.g. a wrong variable reference) discovered in the affected code while already restructuring that section, rather than leaving them. Confidence: 0.75

- Prefers configuration-driven, generic engines over hard-coded, product-specific models: when the domain varies across businesses (steel vs. cement vs. paint), the data model and UI must let each business configure its own products → categories → attributes → variants and have the same engine handle everything — explicitly "CONFIGURATION-DRIVEN, NOT PRODUCT-SPECIFIC". Forbids hard-coded domain fields (Grade, Brand, Factory, Gauge…) and any `if product === "x"` conditional form logic; the UI renders whatever the configuration defines. Confidence: 0.85
- Prefers stable IDs and deterministic identity keys over display names for identity: entities like variants must be deduplicated by a normalized internal key (e.g. categoryId + sorted attribute key=value pairs), and records must never be identified or matched by their human-readable display name. Confidence: 0.7
- Renders primary record displays from the stored hierarchy rather than pre-computed display strings: resolve product/category names from their stored IDs and expand `attributeSnapshot` into per-attribute lines; a variant's `shortName` ("DG Khan Cement · 53 OPC") is only a compact display shortcut for other surfaces, never the primary structured representation of a row ("Very important: don't use shortName as the entire display"). Confidence: 0.85
- Keeps business-entity references (supplier, customer, warehouse/location, prices/rates) as separate transaction-level fields rather than baking them into the product definition as attributes — supplier belongs to the purchase/lot, never to the variant/product identity. Confidence: 0.6

- Repository is restructured into a client/server split at the user's explicit request: the entire Next.js app (`src/`, `public/`, `package.json`, lockfile, and all configs) lives in `client/`, and `server/` is an intentionally empty scaffold (`.gitkeep`) reserved for the future backend. All builds, installs, and dev servers now run from `client/` (`cd client && npm run dev`); file moves for such restructures use `git mv` so history follows the files, and project docs (ARCHITECTURE.md) are updated to match the new layout. Confidence: 0.85
- All project documentation is centralized in a single `docs/` folder at the repository root — explicitly requested: one folder where "all the context, all the architecture.md, front end design.md, APIs.md — everything will be there." Existing docs (ARCHITECTURE.md, NUMBER_AUDIT.md) move in via `git mv` so history follows, and new guides get written there too: docs/frontend-design.md captures the design system (colour tokens, typography, layout/UX conventions, shared components) and docs/apis.md records the current client data API plus the REST contract the future server/ must implement. README.md is refreshed to describe the layout and link every doc, and all cross-references to moved docs are grepped and fixed so nothing dangles. Confidence: 0.85

## Data fetching & loading
- Avoids useEffect-driven data fetching: the user ties repeated/stray useEffect loads directly to UI glitches ("don't use useEffect in any place like repeatedly — it makes a glitch") and asks for a smart query layer (React Query). When the project has no query library installed, they accept a targeted fix inside the existing store (explicit ready flags, one managed load) over adding the dependency — but new fetching must never be scattered across useEffects. Confidence: 0.6
- Wants fetched page data cached across in-app navigation: revisiting a page (or switching tabs away and back) must render instantly from cache with zero new API calls — the user filed the Sales & Invoices page refetching from the database on every visit as a bug ("why we are not using caching in this … when we change the tab and comes again … it again refresh the data"). Data should refetch only when a real mutation happens (new invoice/sale/payment) or on a full page reload. Accepted mechanism: a module-level page cache inside the shared pagination hook (`use-server-paginated.ts`), keyed by `path?page&limit`, each entry stamped with the store's `dataVersion` at fetch time — a version-matching hit mounts with its data and no spinner, per-page entries make pagination flips instant, and the version bump on any ledger mutation invalidates stale entries so figures stay correct after recording a sale; in-memory cache means a reload naturally fetches fresh. Verified by counting `/sales` network requests across navigate-away-and-back (zero new) vs. reload (refetch). Confidence: 0.85
- Duplicate fetches on a page load are bugs to eliminate at the shared root, not per page: the user twice reported "4 API calls on refresh" in the network tab (Reports page, then Sales & Invoices) and both traced to the same multiplicative cause — the store bumping `dataVersion` twice per refresh cycle (once after `/ledger/bootstrap`, once after `/ledger/transactions`) × React Strict Mode double-mounting effects. Conventions established: a cache-invalidation version signal bumps ONCE per refresh cycle (in `refreshCore`/`refreshFull` after the bootstrap — never inside `applyBootstrap` or per-load steps; consumers treat it as a coarse "ledger changed" signal, which also keeps the cache invalidated even if the transactions load fails), and shared fetch hooks keep an in-flight promise map keyed by cache key + dataVersion (`inFlightPages` in `use-server-paginated.ts`, mirroring the earlier `server-report.ts` dedupe) so a duplicate effect run at the same version shares the pending request instead of firing a second. Accepted verification: count the endpoint's network requests — fresh load exactly 1 (was 4), tab away-and-back 0 (cache), mutation-triggered refetch behavior unchanged. Confidence: 0.8

## Performance
- Prefers memoizing derived/lookup computations (`useMemo` for maps and filtered arrays) instead of recomputing `.find()`/`.filter()` scans inline in the render body on every keystroke, so large inventories don't jank. Confidence: 0.8
- When an endpoint is slow, diagnose with measurements before touching code: run the project's own perf-audit harness for a baseline and check its index data first — the audit proved indexes were already correct (index scans at 0.07–0.2ms) while each DB round-trip cost ~150–200ms, so latency is bound by the NUMBER of sequential queries, not per-query cost. The fix is structural round-trip reduction (one bulk fetch after the first page instead of paging 100 rows at a time; batching independent lookups into a single `$transaction([...])`), not hunting for missing indexes that aren't missing. Reconfirmed on the Profit & Reports page in a second form: `reports.service.ts` awaited ~10 independent queries one-by-one against the remote Neon Postgres (~100ms network RTT each → ~1s warm per call) and a dead `purchases` query was fetched with all its lines but never used — restructure reads into concurrent promise phases (all independent queries start together and are awaited once via `Promise.all`; only queries needing an earlier result, like cost-purchases after the sales list, wait one phase) and delete fetched-but-unused queries. Measured warm time dropped ~1s → 0.5–0.7s. Confidence: 0.8
- Prove performance fixes with before/after numbers from the project's own audit harness — baseline first, change code, re-run the identical audit, report a measured comparison table ("real measured numbers, not guesses") — rather than asserting improvement from code reasoning alone. Confidence: 0.75

## Git workflow
- When a batch of work is done, expects the agent to persist it via the full git flow in one go — stage the changes, commit, and push to the current branch on origin (asked tersely: "commit and push" / "commit and push all the changes", i.e. everything sitting in the working tree; and again bundled into the task request itself: "…remove all the mock data and please then make a commit and push it"). Confidence: 0.65
- When asked to commit, stage only the task's source files (`git add <specific paths>`) rather than the whole tree — auto-managed dirs like `.commandcode/` and untracked non-task files (e.g. `AGENTS.md`, `CLAUDE.md`) stay out of the commit. Confidence: 0.6
- Commit messages follow a short summary-subject + bulleted body format, each bullet a substantive change, ending with the `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer. Confidence: 0.6

- Once a feature branch's work is done, wants it merged into `main` (the project's integration branch) and the result pushed to origin — requested tersely as "I want you to merge other branch into the main branch" — rather than leaving the branch dangling; comfortable delegating the whole merge (branch inspection, divergence handling, push) to the agent. Confidence: 0.55

## Tooling & environment
- Develops on Windows with cmd as the shell: heredocs (`<<'EOF'`) don't work, so for multi-line git commit messages write the message to a temp file and commit with `git commit -F <file>`. cmd also has no Unix-style inline environment variables — `VAR=value command` fails, use `set VAR=value&& command` (e.g. `set ITERATIONS=5&& node scripts/...`) — and redirect discarded output to `NUL`, never `/dev/null`. Confidence: 0.9
- Background preview servers outlive their shell on Windows: a background `npm run start` (`next start`) keeps serving after its wrapper task is stopped or killed, leaving a detached node process holding the port (a stale server even answered HTTP 200 against the new build). After verifying, find the listener by PID (`netstat -ano | findstr :3000` → `taskkill /PID <pid> /T /F`) and confirm the port is free before finishing. Confidence: 0.6
- When report/derived figures are disputed or money math changes, verify the calculation engine directly instead of eyeballing code: compile the pure lib modules to CommonJS in the scratchpad (`npx tsc src/lib/<modules>.ts --outDir <scratchpad> --module commonjs --target es2020 --moduleResolution node --jsx react-jsx --esModuleInterop --skipLibCheck`), then run a `node -e` harness (point `NODE_PATH` at the project's `node_modules` when React is in the graph) that builds the report across every seed month and asserts the invariants with printed per-period numbers — stock identity `Opening + Purchase − Sold = Remaining` at zero tolerance, and the chain rule (closing Remaining == next month's Opening, qty and value). This is how a seed bug (a sale dated before its stock existed) was proven rather than guessed. The same harness also proves new scoping/attribution logic before the UI is trusted: inject synthetic records for the scenario under test (e.g. a shop-wide Transport expense plus a product-tagged Labour expense) and print the per-scope results (All Products / each product) to confirm the filtering rules. When new display figures are added on top of untouched money math, the harness also asserts the profit identity to the paisa (netProfit = profitOnSales − expenses, unchanged from before the change) and reconciles each new figure against an independent sum recomputed from the raw records (e.g. summing the seed purchases' transport fields and requiring exact equality with the panel figure — 48,000 = 48,000). Confidence: 0.8
- The machine's global npm config sets `omit=dev`, so a plain `npm install` silently skips devDependencies (TypeScript, `@tailwindcss/postcss`, NestJS CLI, etc.) and later builds fail with missing-package errors — it bit the `client/` install and again the new `server/` install. For dev work install with `npm install --include=dev` rather than modifying the user's global npm config. Confidence: 0.85
- The machine also exports `NODE_ENV=production` globally, so any code or config that branches on `NODE_ENV` misfires during development: `next.config.ts`'s `NODE_ENV === "production"` check made even `next dev` act as production (the CSP lacked the dev-only `'unsafe-eval'` that Next.js HMR/React DevTools require, and HSTS leaked into dev headers; Next also warned about the non-standard NODE_ENV). Never trust `NODE_ENV` for environment detection in this repo — derive the phase from the framework's own signals instead (Next.js `PHASE_DEVELOPMENT_SERVER` / `PHASE_PRODUCTION_BUILD` / `PHASE_PRODUCTION_SERVER` constants passed to the config function). When relaxing a strict security header for dev (e.g. `'unsafe-eval'` in `script-src`, allowing `fonts.googleapis.com`/`fonts.gstatic.com` in `style-src`/`font-src`), keep production strict and gate the relaxation on the phase, not the env var. Confidence: 0.85

## Backend engineering (user's written Tradex spec)
- Backend stack is fixed by the user's written spec: Node.js + NestJS (Fastify adapter) + TypeScript strict mode + Prisma + PostgreSQL hosted on Neon, REST versioned under `/api/v1` — "use exactly this stack unless there is a documented technical reason to change it." Prisma is the sole DB access layer (raw SQL only when a complex query genuinely benefits); Neon is just the Postgres host, never treated as a separate database or a place for Neon-specific APIs. Confidence: 0.95
- Architecture is a modular monolith — one NestJS application, multiple domain modules (auth, users, products, inventory, purchases, sales, customers, suppliers, payments, invoices, reports), one PostgreSQL database. Explicitly forbids microservices, Kubernetes, Redis, message queues, or other infrastructure "unless there is a concrete requirement"; keep modules separable so services can be extracted later only if truly needed. Confidence: 0.95
- Controllers stay thin (HTTP concerns only); business logic lives in services, with modules split by business domain. Confidence: 0.9
- Financial correctness rules are binding: money is never JavaScript floats (Postgres numeric / Prisma `Decimal`); multi-record business operations (sale + items + inventory + customer debit + invoice) run atomically inside `prisma.$transaction` and must roll back completely on failure — "do not allow partially completed financial transactions." Confidence: 0.9
- Design the database around transactions and history, not current balances: customer/supplier balances and inventory quantities are derived from records, never stored-and-overwritten; every inventory change writes a traceable ledger row (`InventoryTransaction` with type + reference); payments are separate auditable records that never simply overwrite a balance; the system must always be able to answer "why is this balance/stock this amount, and which transaction produced it." Confidence: 0.9
- Never trust the frontend: validate every external request with DTOs (class-validator — IDs, quantities, prices, dates, required fields, enums, pagination, filters); business rules and authorization are enforced on the backend because "the frontend is not a security boundary" and hiding UI is not access control. Confidence: 0.9
- Secrets and config hygiene: credentials live in `.env` (never committed; keep `.env.example` with variable names only), passwords hashed never plaintext, auth endpoints rate-limited; configuration is centralized in one layer that validates required env vars at startup instead of scattered `process.env` reads. Confidence: 0.85
- Operational rules: schema changes only through Prisma migrations (never hand-edit the production schema); centralized exception handling returns a consistent `{statusCode, message, error}` shape and never leaks DB errors, stack traces, or credentials; all potentially large list endpoints paginate; indexes are added for real query patterns, never blindly. Confidence: 0.85
- Tests target critical financial/inventory logic — purchase & sale creation, inventory calculation, customer/supplier balances, payment processing, profit, auth — especially transactional edge cases (oversell attempt → operation rejected, inventory and balances unchanged). Confidence: 0.85
- Cross-cutting invariants enforced through many manual call sites (e.g. ~23 catalogue-write methods that must each invalidate the bootstrap cache) need a CI-time safety net before an optimization pass is called done: either a source-enumeration test that fails when any method containing a Prisma write lacks the invalidation call, or a centralized invalidation chokepoint — pick one and close it while the cache design is still fresh ("this is the one I'd insist on before calling the whole pass done"), because the failure mode surfaces months later ("someone adds mutation #24"), not in today's test suite. Guard the guard: assert the enumeration still matches the known write methods (count ≥ N plus named methods) so a future refactor can't make the check silently vacuous. Confidence: 0.8
- Pragmatism over premature complexity: avoid unnecessary dependencies, don't optimize prematurely (real bottlenecks are DB queries, indexes, pagination, transactions, connection management), and keep the backend stateless so it can scale horizontally behind a load balancer later; scale vertically first. Deployment intent: frontend Vercel, backend Docker/VPS, Postgres managed on Neon (never run inside the app container). Confidence: 0.8
- When the user supplies a written specification, follow it exactly and document any deviation explicitly (e.g. adding expenses/stock-checks modules beyond the spec's module list because the business already tracks them) rather than silently diverging. Confidence: 0.8
- Before removing a field from an API payload, grep every consumer to confirm it's genuinely dead (bootstrap's `dashboardSummary` burned 8 queries — including a per-purchase correlated subquery — that the client never read), and keep the payload's `version`/contract fields untouched so client cache compatibility survives the slimming. Confidence: 0.7
- Never apply an optimization that carries a security tradeoff unilaterally: caching JWT validation would have cut ~400ms from every request but delays token revocation — surface it to the user as an explicit decision ("say the word if you want it") instead of silently implementing it. Confidence: 0.7

## Verification & bug-fix discipline
- When a fix closes a bug on one state-change path, enumerate every other path that can trigger the same state change and close them all before calling the fix done: walk the API surface and grep the write fields. Wiring `invalidateBusiness` into the subscription PATCH alone would have left "a narrower version of the same bug in an edge path" — the follow-up grep over `subscriptionStatus/billingCycle/subscriptionEndsAt/allowedPages` writes surfaced two more gaps (platform plan edits change `billingCycle`/`allowedPages` for every business on the plan; owner deletion hard-purges logins without a `tokenVersion` bump). A five-minute grep is "worth doing before you consider it done-done." The enumeration also spans sibling UI surfaces: when a bug is fixed on one page, the user asks for the parallel tabs to be audited for the same defect ("look at other like purchase tab also is this a similar bug also fixed there") and expects a definitive yes/no answer either way — reaffirmed for the duplicate-fetch fix with "if it's happening in there I want you to fix there also," which mandated sweeping every other data-fetching page/API across the app (admin pages included) for the identical defect and fixing each occurrence. Confidence: 0.9
- For time/TTL-based logic, verify the exact race condition rather than just the happy path: the fake-clock test that advances time past `subscriptionEndsAt` while the cache TTL is still alive, then asserts the cached request is rejected with zero DB calls, is "the correct way to verify it — that's testing the exact race condition." Confidence: 0.8
- A test or safety net shipped with known blind spots must state its limits inside the artifact itself (a "KNOWN LIMITATION" paragraph in the spec's header comment: static source inspection doesn't follow call graphs and can't prove the invalidate call executes on every code path), so nobody mistakes "CI green" for "provably covered" — and note the strictly-stronger alternative (a runtime test spying on the cache) for when the tradeoff is ever revisited, while accepting the cheaper source-enumeration version as a reasonable tradeoff now. Confidence: 0.85
- Annotate confusable metrics at the point of collection, not just in the chat reply: a number in an audit/report script that can be misread (a cold simulation of JWT validation cost that looks like a live-path measurement) gets a source comment plus a `note` field in its output — the failure mode being prevented is a future engineer seeing that number in the JSON six months later and reopening a closed investigation. Confidence: 0.8
- When reporting a bug, the user frames the fix scope as full-stack — "I want you to fix that bug in client side and server side on both" — meaning both the client behavior and any server-side contribution (e.g. a rate limiter that 429s `/auth/me` under a request burst) must be corrected, not just the surface where the symptom shows. Confidence: 0.65
- Scope post-change checks to what changed: typecheck the affected package (`npx tsc --noEmit`) and run ESLint only on the touched files (`npx eslint <files>`), not the whole app, whose output drowns the signal in pre-existing warnings; when a flagged error survives, confirm it pre-existed (same lines and rules before the change) and report it as pre-existing rather than silently expanding scope. Confidence: 0.6
- In browser verification a disabled control is not a dead end: diagnose why it's disabled (e.g. no invoices in the current month because the seed data lives in Feb 2025) and drive the UI to a state where the data exists (switch the year/month selects) so the flow is exercised end-to-end before declaring it verified. Confidence: 0.55

## Routing & multi-tenant navigation
- Multi-tenant URL invariant: every client-side navigation or history write must carry the `[businessSlug]` prefix. Raw paths — `window.history.replaceState(null, "", "/sales?tab=print")` or `router.push("/sales/print?...")` — silently break routing: Next.js syncs history writes into the router, `usePathname()` then returns the slug-less `/sales`, and the Shell guard reads "sales" as an unknown business slug and bounces the user to `/${slug}/dashboard`. Programmatic paths go through `useBusinessHref()` and links through `BusinessLink`; never hardcode app URLs as bare strings, and when adding a new `history.replaceState`/`pushState`/`router.push`, check how sibling code builds its path first (grepping for the raw pattern catches every instance of the bug class in one pass). Confidence: 0.85
