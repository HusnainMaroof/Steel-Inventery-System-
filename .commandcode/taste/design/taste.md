# Taste

## Visual design
- Prefers a minimal, professional, monochrome UI — roughly 90% black/white/gray — with thin 1px borders, rectangular cards, no gradients, no heavy rounding, and subtle or no shadows. Confidence: 0.95
- Uses a specific neutral design token palette: canvas `#F8F8F7`, cards `#FFFFFF`, primary text `#171717`, secondary text `#737373`, borders `#E5E5E5`, dark highlight card `#111111`. Confidence: 0.95
- Color is reserved for status only, in muted tones: muted red for due/warning and muted green for paid/positive; avoids strong or bright colors elsewhere. Confidence: 0.95
- Card/panel radius is 8px; inputs/buttons slightly smaller (6px); borders 1px solid `#E5E5E5`. Confidence: 0.9
- Keeps generous whitespace: dashboard padding ~24–32px, card padding ~20–24px, card gaps ~12–16px, section gaps ~16–24px. Confidence: 0.8
- Dislikes congested/cramped popups; when an entry modal got too busy, the user's fix is to remove panes/features (e.g. the right-side invoice preview) and fall back to a compact centered modal (roughly 3xl) rather than pushing it near-fullscreen — the goal is a focused, breathable single-column form with clearly separated sections (date/party → items → money → totals). Confidence: 0.8
- Prefers entry modals (e.g. New Sale) as a single clean column without side-by-side panes once a live preview is out of the popup: date/customer on top, then the items list, then discount/tax/paid, with the totals pinned and always visible. The earlier full-height two-pane workspace only applied while a live preview lived in the form, and that pane was removed on the user's request. Confidence: 0.8
- Modal layouts should be responsive: two-pane content (form + live preview) should sit side-by-side only on wide/xl screens and stack full-width below that breakpoint, rather than squeezing both panes onto smaller viewports. Responsiveness of such layouts is an explicit requirement the user calls out. Confidence: 0.85
- Prefers a clean modern sans typeface app-wide (Inter primary, Geist as alternative); small labels set uppercase with letter-spacing and weight 500–600; main numbers bold (600–700) with tabular figures; table text at weight 500; secondary text at 400. Confidence: 0.9
- Uses the black/dark card treatment for exactly one "priority" KPI (the single most important business metric, e.g., Total Stock) rather than making every card prominent. Confidence: 0.95
- Text on black/dark surfaces must stay high-contrast and readable (white) regardless of global CSS: when the black Total row in the sale-detail popup rendered black-on-black because a global `td { color: black }` rule overrode the white utility class, the user flagged it as a bug to fix. Explicit utility color must win over inherited/global element styles on dark backgrounds — wrap dark-surface text in an explicit color span if a global rule would otherwise swallow it. Confidence: 0.6
- List-page summary stats should stay minimal: on Sales/Invoices the stat strip is a record-count card plus one dark "Total outstanding" card — the separate "With balance due" count card was explicitly removed as redundant since the outstanding amount already conveys that. Confidence: 0.7
- Wants the main dashboard to be stats/KPI-only — detailed stat cards (Stock in Hand, Stock Worth, Sales, Profit, Payment Dues, Customer Payment Dues, Mills Payment Dues) and nothing else; explicitly removed the Recent Purchases / Recent Sales lists and the per-item/quality table from the dashboard (those belong on dedicated pages, not the overview). Confidence: 0.85
- Prefers the dashboard to be scoped around a selectable business entity rather than fixed tabbed widget sections: a product dropdown at the top-left ("All Products — entire depot" plus each product) drives every KPI and table below, with all cards/lists filtering to the selected product. Explicitly removed the fixed top tabs (Customer Balance, Outstanding Bill, Recent Purchases, Quick Actions) and the old welcome content in favor of this. Confidence: 0.75
- The dashboard product dropdown should default to the "All" view on load — show the whole depot by default rather than a specific product, with individual products selectable from there. Confidence: 0.85
- Branding/business identity is "New Ittifaq Steel Depot & Cement Agency" — use this name in sidebar, page headers, and other UI copy rather than stale/generic names. Confidence: 0.9
- When the user calls the UI/UX "old" and asks for a "new layout structure", prefers status-driven document layouts over plain tables: per-row Total / Paid / Due columns, small tinted status chips (Paid green, Partial amber, Unpaid red, Advance blue), a summary strip above the list (total invoices, total outstanding), and row-level actions (Receive / Open) instead of boxy stat footers. The Paid/Unpaid chips on Sales/Invoices rows were later removed on request since the Due column already conveys payment state (see the redundancy bullet below). Confidence: 0.7

- In list rows on module pages (Purchases, Sales, Inventory), each row should read like the full business record: supplier → product/item (product and quality stacked beneath the item name, e.g. `3 Sutar` over `Steel · 60 Grade`) → quantity → buying price → selling price — so the user can see what product a row is at a glance without opening it; a row that shows only the item name hides too much. Confidence: 0.8
- Numeric column headers in list tables must be right-aligned so the header label lines up exactly over its values — the user calls misaligned "label and its value" a visible UI bug — and this convention applies to every numeric column (quantity, buying/selling price, total/paid/remaining) across all tables, not just one screen. Confidence: 0.85
- Per-row list actions must stay as explicit buttons, not be replaced by click-to-open: when a row redesign dropped the View/Delete buttons in favor of tapping anywhere on the row, the user asked to "bring back those buttons" — each row keeps a visible View button and a Delete button (with confirmation), and the buttons must stop the row's own click so they don't double-fire. Confidence: 0.8
- Once a redesigned list layout is approved in one section, the same treatment is expected everywhere else — after the All Purchases rows were rebuilt the user said "also fix the payment due" the same way, and once that module was done immediately asked to move "on invoice and sell" and fix the layout overall there too. List rows across the whole app (Purchases, Payment Dues, Sales, Invoices) must share one anatomy — identity on top with a product · quality or invoice-no · items summary stacked beneath, supplier/customer column, right-aligned numeric headers over values, same action buttons, and matching mobile cards — so no screen reads as old/new mixed formats. Confidence: 0.8
- On Sales/Invoices rows the identity should be the actual items sold, not the invoice number — the user asked to drop the invoice-number subtitle ("remove the invoice number just show the item properly what item we have sell") and then to "show the product a bit more": each sold item gets its own line prefixed with its product category (e.g. `Steel · 3 Sutar`, `Cement · Grey Cement`) so the material type reads at a glance, instead of a bare comma-joined string of item names. The invoice number still belongs as the detail popup title and on the printed bill, just not in the list row identity. The plain `Product · Item` prefix was later upgraded: the user asked to "highlight the product and its item" and to show "what product what item then what quality and what quantity", so each sold line now breaks out into an aligned mini-grid of Product (bold/highlighted so it reads first) / Item / Quality grade / Quantity-with-unit — one aligned row per sold line stacked under the customer, on both desktop rows and mobile cards — rather than fusing attributes into a single text string. Confidence: 0.85
- Wants the exact recorded time shown wherever a sale/invoice date appears. Placement on list rows has flip-flopped and currently sits as its own narrow right-aligned column under a "Time" column header (positioned before Total/Paid/Due on desktop): after first asking for the time inside the first cell, the user reversed and asked to "remove the time from [the first] column" and have it live under a proper column header on the right section instead; mobile cards keep the time top-right on the customer line. Also shows `date · time` on the printed bill and the sale-detail popup header; rows within each day-group sort newest-first by recorded time. Confidence: 0.75
- On list rows, avoids showing the same state twice: on Sales/Invoices the user had the separate Paid/Unpaid Status column and its colored badges removed from both desktop rows and mobile cards because the Due figure already says whether a bill is settled — "if we have dues, we are also showing the dues and status, they are both two things — remove the status." Payment state should come through once, via the numbers (a red/emphasized Due amount when outstanding; "Paid"/`—` when fully cleared), not duplicated by a badge or status cell that restates an adjacent amount. Confidence: 0.85
- Data tables on module pages must be fully responsive and lossless: no column or detail — identity, secondary attributes (mill/address/shop), contact, and the row's action buttons — may be hidden or dropped on small screens. When a full-width grid won't fit on phones, the section re-renders as stacked mobile cards that still show every field plus the action button. Explicitly requested for the Mills/Suppliers and Customers pages ("make it responsive, show ... all the details of the table") after those tables had hidden phone/address/action columns below the md breakpoint; mobile card layouts are the accepted mechanism across the app's list pages. Confidence: 0.85
- Prefers readable, non-washed-out secondary text in dense list rows: when asked to "highlight the text a bit more", the detail fields under sold items (item names and quality grades) were darkened and given extra weight — item text stepped from light gray up to darker medium-weight, quality from very light gray to a clearly legible tone — so the product → item → quality → quantity reading stays clear at a glance rather than relying on barely-visible light grays. Confidence: 0.7

## Data entry & flows
- Wants busy/cluttered entry forms redesigned into a spacious modal popup with clearly labelled sections (Date → party → products/items → money), with the New Sale flow mirroring the purchase form's structure for consistency across modules. Confidence: 0.8
- Does not want a live invoice preview embedded in the New Sale entry popup — explicitly asked to remove the right-side invoice preview because the popup felt cluttered and the UX was bad; invoice-style rendering belongs on dedicated saved-sale detail/print surfaces, not duplicated inside data entry. Confidence: 0.85
- Wants derived money values computed automatically and shown live as a full breakdown (Subtotal → Discount → Taxable → Tax → Grand Total → Paid Now → Remaining Due) rather than making the operator do the math by hand. Confidence: 0.85
- Prefers a filter-then-add flow for adding line items (cascading product → item → quality → mill/source dropdowns feeding one “+ Add Item” action; each added item becomes its own card where only quantity is edited inline — unit price is not editable; options surface available stock and the lot's auto sell price). The add-item step must NOT open a pop-up — the user explicitly rejected popup-based adding while creating an invoice (“when I add, don't open a pop-up”): the cascading filter row sits always-visible inline on the creation page and appended items appear as inline cards, so the whole creation flow is free of nested popups. Confidence: 0.9
- Prefers keeping creation flows as popups rather than switching to a dedicated full-page view — but the popup must be screen-sized: “+ New Sale” opens a large overlay taking ~70–80% of the viewport (the sales list stays visible and dimmed behind it) with Cancel/Save in its header; on save the overlay closes and the fresh invoice's detail opens. The earlier full-page creation screen was explicitly rejected in favor of keeping the popup and making it big. Confidence: 0.9
- Prices on customer invoices must be locked, not typed at sale time: when an item is added to a sale, its unit price auto-fills from the stock lot's recorded selling price ("Your Selling Price" set on the purchase) and the added-item row shows that price read-only; if no sell price was recorded, fall back to landed cost + ~15% so the sale can still be saved. Confidence: 0.85
- Modal entry flows (e.g., New Sale, New Purchase) should stay visually consistent with each other so the UI feels like one coherent system — shared section/divider rhythm (date/party → items → money → totals) and matching compact modal sizing rather than a form-plus-preview split. Confidence: 0.7
- On full-page creation views, prefers running totals in a compact right-side rail (Summary card: subtotal, discount %/tax %, grand total, paid now, remaining due, and the Save button) over bottom totals — chosen explicitly when asked between “compact totals panel” and “bottom totals”. The rail is sticky on xl screens and stacks below the content on smaller ones. Confidence: 0.8
- For repeated dense line data (added items, invoice lines), prefers a compact scannable table over stacked bordered cards: a single header row instead of repeating per-row micro-labels (Qty/Price/Amount) inside every card, right-aligned numeric columns, and one row per item. This removes most of the visual repetition at 5+ rows. Confidence: 0.9
- When a single input or action carries the primary weight of a form (e.g. "Paid Now", the settle-now amount, or the commit "Add" button), promotes it with distinct visual weight — own bordered/tinted block (e.g. amber tint + accent border + larger input) so it reads on par with the grand total and is clearly separate from secondary low-frequency controls like Discount %/Tax %. Secondary controls stay as plain small paired inputs. Confidence: 0.85
- Keeps different functional control groups visually separated in creation forms: the narrowing/filter controls (product → item → quality → mill) share one labeled grouped surface (e.g. a light shared background), while the confirm/commit action (qty + "Add Item") lives in its own brief separated by a divider — so the eye reads which fields narrow a search vs. which commit a value. Confidence: 0.8
